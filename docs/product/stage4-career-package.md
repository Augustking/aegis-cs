## 1. 双项目差异化定位

| | MewHelp（项目一） | Aegis-CS（项目二） |
|---|---|---|
| 解决的问题 | 答得准：检索、生成、评估 | 答得稳、兜得住：质量管控、人工闭环、工程交付 |
| 核心技术纵深 | RAG 混合检索（BGE-M3+BM25+RRF+精排）、置信度校准、RoBERTa 微调+ONNX | LangGraph 状态机编排、接地质检（grounded judging）、前后端分离、持久化与容器化 |
| 质量手段位置 | 生成**前**（证据校验+置信度） | 生成**后**（LLM-as-judge+一票否决） |
| 数据闭环 | 数据飞轮写回知识库 | 决策轨迹回放定位坏例 |
| 叙事一句话 | 一个深检索的智能客服引擎 | 一个带质量管控和坐席协作的完整客服系统 |

## 2. 指标口径（重要修正）

- **"误拦率"旧口径不严谨**：25 道业务题被转人工的比例≠误拦率（未人工核验回答确实合格）。简历表述应为"**业务问题转人工比例**"，或标注"未经人工逐条核验"。
- 质检拦截率的 10 条坏例是构造样本，非线上自然分布，表述用"**构造坏例集拦截率**"。
- 延迟为单会话串行口径（含 3 次 LLM 调用），注明模型档位。
- 最终数字以 2026-09-07 复跑报告为准（见 `evals/results/eval_report.md`）。

## 3. 简历项目描述（定稿草稿）

## 智能客服系统 Aegis-CS（独立完成，2026.7–9，GitHub 开源可复现：github.com/Augustking/aegis-cs）

技术栈： Python、LangGraph、LangChain、Flask、Vue3、Element Plus、Pinia、SSE、SQLite、Docker Compose、pytest

项目介绍： 面向电商售前售后场景的多智能体客服系统。以 LangGraph 编排"意图分类—领域专家应答—回复质检—人工接管"主链路，配套客户咨询端与坐席工作台（前后端分离），构成"AI 先答、AI 自审、人工兜底"的完整质量链路。

个人职责： 独立完成整体架构设计与全部模块实现，涵盖多智能体编排、接地质检与转人工链路、双端前端、身份与权限边界、持久化与容器化部署
- 设计答后质检链路：LLM-as-judge 按相关性/解答度/可信度三维打分，业务智能体检索到的数据上下文作为证据随消息下发（接地质检），证据无依据的具体承诺可信度计 0 分并一票否决转人工；质检链路自身故障按满分放行（fail-open），从设计上杜绝质检单点故障导致全站瘫痪
- 设计人工接管闭环：低分回答作为草稿留存工单（不下发用户），会话挂起期间不再消耗模型调用；坐席处理结果写回对话上下文，AI 恢复接管并引用人工结论连续作答
- 交付客户/坐席双端前端（Vue3 前后端分离）：客户咨询窗、坐席三栏处理台（草稿采纳/修改、质检依据、决策轨迹回放）、工单实时推送；坐席登录与会话归属校验在服务端强制（跨访客读取返回 403）
- 建立评测与定标体系：自建 30 题六桶分类集与 10 条构造坏例集，意图分类准确率 96.7%，构造坏例拦截率 100%（接地质检+一票否决，阈值 6 经拦截率-转人工比例扫描定标）；27 个单元/集成测试 + 六场景端到端验收剧本 + Docker Compose 部署

技术亮点：
- 接地质检（grounded judging）：实测发现无接地 LLM-as-judge 对编造回复给满分（无法分辨"答得自信"与"答得真实"），将业务数据上下文作为证据下发给 judge 后，编造回复可信度被正确压至 0 分——这是该系统最核心的设计决策
- 模型分层路由：分类/质检/应答走独立模型通道（CLASSIFY_MODEL / JUDGE_MODEL 可配），judge 选用指令遵循更强的模型档并关闭思维链，单轮 p50 延迟从 82s 降至 19.8s
- 小模型输出工程：实测 7B 模型对嵌套 JSON 输出不可靠（分类器被 markdown 示例带偏、judge 嵌套 dims 大量截断失真），分类提示词重构为行内格式、judge 改为扁平 key=value 格式并以"维度分相加"合成总分，解析双格式兼容且 fail-open
- 工程化交付：对话状态经 checkpointer 持久化（服务重启可恢复）、结构化日志（request_id 贯穿 + PII 脱敏）、Docker Compose 一键部署、六场景验收剧本可一键复现

## 5. 面试追问准备（5 问 + 回答方向 + 代码位置）

1. **"96.7% 分类准确率怎么来的？样本才 30 个"** — 六桶均衡构造集，错误全部可归因（跨域语义如"补发赠品投诉"）；样本小是诚实的局限，下一步是扩容与 few-shot 迭代。代码：`evals/eval_set.json`、`tools/query_tools.py`
2. **"转人工比例 20% 不影响客户体验吗"** — 口径上这不是误拦率（未经人工核验），且含非对称代价决策：漏放编造承诺引发售后纠纷（不可逆），多转一单人工只是坐席成本（可逆）；扫描显示阈值再降误拦收益有限而拦截率下滑——定标是权衡不是拍脑袋。代码：`evals/run_eval.py` report 阶段
3. **"质检自身挂了怎么办"** — fail-open 按满分放行 + 结构化日志告警；质检不可用只降级为"无质检"（回到原始系统行为），不会放大故障。代码：`quality_check_node` 异常分支
4. **"无接地 judge 为什么会失效"** — 实测：judge 只看问答对时给编造回复满分（无法验证事实）；把 Agent 检索到的证据下发后 faithfulness 才有判据。这是"评估器需要和被评估者同样的上下文"的一般性结论。代码：`build_judge_messages(evidence=...)`、`human_handoff_node`
5. **"单服务 + SQLite 能扛多少并发"** — 不硬扛：当前是单商家演示/私有化交付形态；扩容路径明确（Postgres checkpointer、工单库迁 PG、SSE 换消息队列），并且架构上已预留（CHECKPOINT_DB DSN、数据访问层接缝）。诚实优于吹牛。
